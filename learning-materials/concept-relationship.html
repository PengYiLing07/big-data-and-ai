🧭 一、学习目标

  • 能一句话说清三者各自扮演什么角色，并说明它们为什么不是三个孤立名词。
  • 能画出「上下文 → Agent」「Skill → 上下文」「Skill → Agent」三条关系，并说出每条关系的作用方向。
  • 能解释「上下文的质量决定 Agent 的表现」这一判断的来由。
  • 能说明 Skill 凭什么「装很多却不挤爆上下文」，以及它不能做什么。
  • 能把三者串成一条完整工作流：从一次请求到产物落盘、再到方法沉淀复用。

❓ 二、核心问题

  • 三个概念分别解决什么问题？把它们放在同一张图里，谁在影响谁？
  • 上下文里究竟装着什么，它凭什么能左右 Agent 的判断质量？
  • Skill 平时占多少上下文？它是怎么做到「按需注入」的？
  • 三者的边界在哪里——哪些事它们各自做不到？

📖 三、概念的通俗解释

这三个概念不是三个孤立名词，而是同一条工作链上的三个环节： 上下文（Context）是 Agent 的「视野与工作记忆」， Agent 是在这份上下文上反复「想 → 做 → 看」的执行体， 而 Skill 是把「怎么处理一类任务」的方法提前沉淀成可复用的说明书， 让 Agent 在有限的上下文里更聪明、更省地干活。

三者可以概括为「容器 / 执行者 / 方法库」的关系：上下文是容量有限的容器， Agent 是在容器视野内推理并行动的执行者，Skill 是按需把流程知识注入容器的方法库。 三者的连接点在于：容器里此刻装着什么，直接决定执行者这一步会怎么做。

💡 一个类比 三者可类比为一间工作室里的三样东西： 上下文是那张工作台面——台面就那么大，此刻摆着什么，决定了手头能做什么； Agent 是台前干活的人——看一眼台面、想一步、动一下手、再看结果，如此往复直到把活干完； Skill 是墙边的一摞岗位手册——每本封面只写「这本讲什么、什么时候用」（体量很小）， 只有接到对应任务时才把那一本翻开摊到台面上。 台面干净、只摆当前要用的东西，人就干得准；台面堆满无关杂物，人就会看漏关键的那张纸。

⚙️ 五、核心机制 / 组成

1. 逐对关系：谁在影响谁

关系说明
上下文 → Agent
（视野决定表现）		 Agent 每一轮决策都只基于「当前上下文窗口里有什么」。上下文给了它：它是谁（系统提示）、对话到哪了（历史）、刚查回什么（工具结果）。 关键：上下文越相关、越无噪声，Agent 判断越准；上下文被撑爆或关键信息被挤掉，Agent 就会“忘事/跑偏”。所以 Agent 的能力上限，很大程度取决于它能否高效利用有限的上下文。
上下文 ← Skill
（Skill 改变“进什么上下文”）		 Skill 平时不进上下文（只有 name + description 占极小空间）；一旦被触发，它才把「怎么做这类任务」的正文、参考、脚本读进窗口。 作用：让 Agent 在不预先占满上下文的前提下，需要时立刻获得专业流程知识。Skill 其实是「上下文内容的生产者和节流阀」——按需注入、用完即走。
Agent ← Skill
（Skill 增强 Agent）		 Skill 让同一个通用 Agent 能“临时变身”成专家：处理 PDF、写报表、做数据分析……本质是给 Agent 追加可复用的行为包。 它也反过来体现了「沉淀」——把做过一遍的有效方法固化，下次不用重新摸索。

2. 上下文如何影响 Agent 的工作（重点）

  • 决定“它知道什么”：系统提示定义了 Agent 的角色与边界；放进的参考与知识决定了它答题的依据范围。
  • 决定“它记得什么”：多轮任务里，历史让 Agent 记住已完成的步骤与约束；上下文越长，越依赖摘要、检索等手段保住关键信息。
  • 决定“它怎么执行”：调用哪个工具、下一步怎么走，都依据窗口里此刻的信息与工具定义。噪声太多会干扰判断（丢了西瓜捡芝麻）。
💡 一句话 上下文是 Agent 的「工作台」，Agent 的所有聪明都建立在「工作台上此刻摆了什么」之上——摆得好，它就高效；摆得乱或摆不下，它就出错。

3. Skill 沉淀可复用任务知识的三个层面

层面做法收益
复用把做过一遍的有效流程写成 SKILL.md（怎么做、注意什么、调什么脚本）。下次同类任务直接调用，不再重复贴长提示词，也不易遗漏步骤。
共享项目级 Skill 放进仓库技能目录，随 git 提交。团队或未来的自己，克隆仓库即获得同一套方法，学习成果统一落盘。
省上下文靠渐进式披露：平时只加载元数据，需要时才载入详细内容。可同时携带大量技能而不挤爆上下文，反而让 Agent 更“专业”。

4. 一条完整工作流

# 以本仓库的 concept-learner 为例，走一遍完整链路 用户：“搞懂 Agent 这个概念” ↓ 命中 concept-learner 的 description Skill 触发 → 把“如何产出概念资料”的方法读进 上下文 ↓ Agent 在这份上下文上：想（规划九个板块）→ 做（联网核查来源）→ 看（对照自检清单） ↓ 写出 agent.html，落盘 learning-materials/ ↓ 人工核查 → 修改 → commit & push（沉淀进 GitHub） 下次学任何新概念，同一套 Skill + 上下文 → Agent 自动复用

这条链正好说明：上下文提供“此刻该知道什么”，Agent负责“据此把事办成”，Skill保证“办这类事的方法被反复用好、沉淀下来”。三者环环相扣。

✅ 核查说明（人工） 「上下文 → Agent」「Skill 按需加载」「Skill 沉淀可复用知识」三条结论分别取自上下文窗口资料与 Anthropic 官方 Agent Skills 文档，多来源一致后采信。 「容器 / 执行者 / 方法库」的口径、以及工作室类比喻属于帮助理解的综合概括，不是某来源原文，故单独列出。

🚀 六、一个具体应用场景

场景：一个课程仓库里，用项目级 Skill 完成一次「新概念学习」任务。

背景：仓库里已装好 concept-learner 技能，它规定了一份概念资料必须包含哪九个板块、图解要满足哪些硬性规范、来源如何核查。现在要学一个新概念——向量数据库。

步骤发生了什么三者各自的作用
1 提出请求输入「学一下向量数据库这个概念」。此时三者都还没动；上下文里只有对话本身。
2 命中技能请求与某技能的 description 匹配，Agent 去读该技能的说明书正文。Skill 从「只占封面的手册」变为「翻开的那一本」。
3 装配上下文方法（九个板块的要求）+ 目标（学向量数据库）+ 已有资料（仓库里同批页面的写法）一起进入窗口。上下文完成装配，成为 Agent 这一刻的全部依据。
4 执行与核查Agent 规划结构 → 联网核实关键论断与来源 → 产出内联 SVG 图 → 按三档难度出题并自测判分逻辑。Agent 在有限窗口内循环推进，把目标拆成可交付的产物。
5 落盘与沉淀产物写入 learning-materials/，人工核查后提交仓库。Skill 的价值在此固化：下次同类任务直接复用，不必重讲要求。
⚠️ 对照：如果没有 Skill 会怎样 同一个任务会退化成「每次把长篇要求重新贴一遍」：步骤容易漏、格式容易走样、来源核查标准每次都要重新约定； 而且这些要求会长期占着上下文，挤压真正用于思考的空间。差别不在于“存到了文件里”，而在于“平时不占地方、需要时才整本翻开”。

这个例子正体现了三者关系的实用价值：上下文决定这一次能想多清楚，Agent决定这一次能把事办到多完整，Skill决定下一次还能不能一样快。

⚠️ 七、易混与边界

  • 易混 1｜上下文 ≠ 长期记忆：上下文是「本次任务的工作台」，任务结束即失效；跨会话保留信息要靠外部存储（写文件、数据库、检索）。把两者混为一谈，就会误以为「聊过一次它就该记住」。
  • 易混 2｜Skill ≠ 把长提示词存成文件：差别不在「存放位置」，而在加载时机——平时只占 name + description 的极小空间，被触发才读入正文。若一个技能的设计是每次都必须整篇加载，那它就丢掉了技能最核心的优势。
  • 易混 3｜Agent ≠ 更聪明的模型：Agent 的「会办事」来自模型 + 工具 + 上下文 + 编排循环的组合。换成更大的模型并不自动等于能独立办成多步任务；工具与编排缺一，能力就不成立。
  • 边界 1｜上下文不是越多越好：窗口有硬上限；同时，输入越长，模型对中段信息的利用越容易衰减，无关内容还会稀释信号——「塞满」往往等于「变差」。
  • 边界 2｜Skill 不能提升模型能力：它提供的是流程知识、参考资料与可执行脚本，不改变模型参数。任务本身超出模型能力范围时，装再多技能也无法凭空办到。
  • 边界 3｜三者都不是免费的：上下文占用对应成本与延迟，Skill 的触发会引入加载开销，Agent 的多轮循环也会累积消耗。用更长的上下文或更多的循环去换效果，通常存在边际递减。
✅ 核查说明（人工） 「上下文有上限」「长输入中段信息利用衰减」「无关内容稀释信号」三条依据上下文窗口官方文档与相关研究资料；「Skill 不改变模型参数」依据 Agent Skills 官方文档对技能本质（指令 + 资源）的界定。 上述边界表述为综合多来源整理，未逐字引用原文。
