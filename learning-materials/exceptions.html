📖 三、概念的通俗解释

Python 的错误至少可以分为两类：语法错误与异常。语法错误又称解析错误，代码连解析都过不去，程序根本不会开始执行，因此它无法被 try 捕获。异常则是「语句或表达式语法正确，但执行时仍可能触发」的错误，例如把不能转成整数的内容交给 int()、用不存在的键去取字典的值。能被处理的只有异常。

异常发生时，程序不会立刻无声退出，而是沿着调用关系一层层向上报，打印出一段堆栈回溯（traceback）。这段信息的信息量很大，但阅读顺序只有一个方向：从最后一行往上读。错误信息的最后一行说明遇到了什么类型的错误，并给出出错细节；紧挨着的 File 行指出出错的那一行代码在哪个文件的哪一行；再往上则是「谁调用了谁」的链条。第一行 Traceback (most recent call last): 本身就在提示这个顺序——最后一次调用显示在最下面。

异常处理则是给程序准备一套备用预案：把可能出错的代码放进 try，把「出了某种错该怎么办」写进 except，把「一切正常时接着做什么」写进 else，把「无论成败都必须完成的事」写进 finally。于是，一行坏数据不再等于整个流程报废——它只是让这一次循环走进 except 分支，剩下的行照旧处理。

💡 一个类比 异常处理可类比为编辑流程里的退稿预案：正常流程照旧推进（try）；遇到某类具体问题就走对应的处理通道（except）；一切顺利时才会执行后续的正式发布动作（else）；而不论这次是否出问题，都要做的那件事——比如把这一期的处理记录记入台账（finally）——都会照做。这一类比属于帮助理解的通俗化说法，非官方原文。
💡 一个类比 报错栈可类比为一份从一线到总部的转呈记录：最下面那一行是最终被认定的事实（是什么类型的错误、具体原因是什么），越往上越接近最初提出请求的那一方。想知道「到底哪里坏了」，最先看的永远是最后一行。这一类比属于帮助理解的通俗化说法，非官方原文。

⚙️ 五、核心机制 / 组成

异常处理由「识别错误—定位错误—决定怎么处理」三步构成：先分清自己面对的是语法错误还是异常，再通过报错栈定位到具体代码行，最后用四个子句把处理策略写下来。

try 语句的四个子句

子句何时执行作用 / 说明
try总是最先执行放入可能引发异常的代码。异常处理程序不仅会处理 try 子句中立刻发生的异常，还会处理在 try 子句中调用（包括间接调用）的函数所引发的异常。
excepttry 子句引发了与某个 except 匹配的异常时按类型是否匹配来决定走哪一个分支。常见模式是打印或记录异常，然后重新触发（用裸 raise），允许调用者也处理这个异常。
elsetry 子句没有引发异常时必须放在所有 except 子句之后。用它比把代码塞进 try 子句更好，可以避免意外捕获非 try…except 保护的代码所触发的异常。
finally任何情况下都执行try 语句结束前执行的最后一项任务；不论是否触发异常都会执行。适合释放外部资源（文件、网络连接等）。

🚀 六、一个具体应用场景

一批稿件数据汇总到一起后，里面常常混着几种脏数据：某一行缺了「字数」字段；某一行的字数是「约三千」这样的文字；某一行的标题只剩空格；甚至整行都不是字典。若不做处理，第一个坏行就会让程序整体崩掉，前面已经处理好的行也一并作废。把每一行的处理放进 try，坏行记入跳过清单，好行照常收下，程序就能跑完全程并交出一份「可用数据 + 问题清单」。下面的代码可以直接运行。 

# skip_bad_rows.py —— 坏行跳过，好行继续跑完
rows = [
    {"标题": "地铁票价调整方案公布", "字数": "18"},
    {"标题": "社区加装电梯推进难点", "字数": "15"},
    {"标题": "   ", "字数": "9"},        # 标题为空
    {"标题": "夜经济观察", "字数": "约三千"},  # 字数不是数字
    {"标题": "老旧小区改造"},                # 缺少「字数」字段
    None,                                      # 整行都不是字典
    {"标题": "城市绿道使用调查", "字数": "22"},
]

ok, bad, processed = [], [], 0
for i, row in enumerate(rows, start=1):        # i 是行号，便于写进问题清单
    try:
        title = row["标题"].strip()
        words = int(row["字数"])
        if not title:
            raise ValueError("标题为空")      # 自己判断出的问题，主动触发
    except KeyError as err:                    # 字段缺失
        bad.append((i, f"缺少字段 {err}"))
    except TypeError as err:                   # 这一行不是字典
        bad.append((i, f"这一行不可用：{err}"))
    except ValueError as err:                  # 内容转不成整数、或标题为空
        bad.append((i, f"字段内容不可用：{err}"))
    else:                                      # 只有 try 里全程没出错才执行
        ok.append((title, words))
    finally:                                   # 成败都记账
        processed += 1

print("总共处理", processed, "行")
print("可用", len(ok), "行：", ok)
print("跳过", len(bad), "行：")
for i, why in bad:
    print("   第", i, "行：", why)
print("可用稿件总字数", sum(w for _, w in ok))

这一段是文章级别的示例，用于说明「坏行不拖垮整体」的处理思路，属于辅助理解示例，非某个来源的原文代码。运行结果是：共处理 7 行，其中 3 行可用、4 行被跳过并记入清单，可用稿件总字数 55。这里的三个 except 子句分别对应官方《内置异常》文档中 KeyError、TypeError、ValueError 的定义场景，else 与 finally 的行为见第五节表格。

⚠️ 七、易混与边界

  • 语法错误与异常不是一回事。语法错误又称解析错误，出现在代码解析阶段，程序尚未开始执行，因此无法用 try 捕获；异常是语法正确但执行时被检测到的错误，可以被处理。把 SyntaxError 写进 except 并不能让一段语法错误的代码跑起来——它压根没进入运行阶段。
  • except 与 finally 的分工不同。except 是条件执行的：只有异常类型匹配时才走；finally 是无条件执行的：不论是否触发异常都会执行，是 try 语句结束前执行的最后一项任务。释放文件、网络连接这类外部资源，官方建议的落点正是 finally。
  • 「处理了异常」不等于「把异常吞掉」。如果在 except 里既不记录、也不重新触发，异常就此消失，后续逻辑会在一个不正确的状态上继续跑，问题被推迟到更难定位的地方才暴露。官方给出的一种常见模式是：打印或记录异常，然后用裸 raise 重新提出，允许调用者也处理这个异常。
  • 捕获范围写得太宽，会连「不该被拦下」的异常一起拦下。按官方给出的内置异常层级，KeyboardInterrupt 与 SystemExit 直接派生自 BaseException，并不在 Exception 之下；因此裸 except: 会把它们一并捕获，而 except Exception: 不会。这也解释了为什么通常按具体类型分别写 except 分支，并且把最宽的那一类放在最后。
  • except 子句的先后顺序会影响匹配结果。多个 except 子句按书写顺序依次匹配，一旦命中就不再尝试后面的分支。把范围宽的写在前面，后面写得再具体也不会被用到。
  • else 不是「无论如何都执行」。它与 finally 的语义完全不同：else 只在 try 子句没有引发异常时执行；把本该保护范围之外的代码写进 try，反而会意外捕获不属于这里的异常。这正是官方建议用 else 而不是扩充 try 的原因。
  • 主动触发异常是一种正常的控制手段。当程序自己发现了业务层面的问题（例如标题清洗后变成空串），可以用 raise 主动触发一个异常，让它和「库函数报的错」走同一条处理通道。raise 唯一的参数必须是异常实例或异常类；传入异常类时会通过调用无参构造函数隐式实例化。
