📖 三、概念的通俗解释

上下文窗口指的是语言模型在生成回答时可以参考的全部文本，其中也包括它自己正在生成的回答。 它和模型训练时"记住"的海量知识不是一回事：训练得到的知识是长期固定的，而上下文窗口是一次请求内的临时工作区， 回答结束后并不会自动保留到下一次会话。
窗口的大小以 token 计量。token 是模型处理文本的最小单位，可能是一个字符、一个词的一部分、一个完整的词， 甚至一小段短语，不同模型的分词方式不同。粗略估计，英文中 1 个 token 约等于 0.75 个词。 一次请求中，系统提示、工具定义、历史对话、工具返回结果以及本次输入，全都占用这同一份预算； 模型生成的输出同样计入其中——输入与输出共享一个上限，而不是各自独立。

💡 一个类比上下文窗口可类比为模型的工作台面，而训练得到的知识相当于它身后那座藏书固定的图书馆。 图书馆很大且不会改变，但台面一次只能摊开有限的几页纸。想让模型此刻推理什么，就必须先把材料摊到台面上； 台面铺满后，旧纸页会被挤下去，除非刻意把它们重新放回来。这也解释了一个容易被忽略的点： 新开一次会话相当于把台面清空，若应用没有主动把先前信息重新送入，模型并不会"记得"上一轮谈过什么。

⚙️ 五、核心机制 / 组成

从"一次请求"的视角看，上下文窗口可以拆成三类内容。它们的更新频率与体量差异很大，这也是上下文管理的着手点。

组成部分作用 / 说明
静态层（系统提示、工具定义）角色设定、行为规则、可用工具清单。每轮都随请求发送，内容基本不变，适合做缓存以降低成本。
动态层（历史对话、本次输入）此前所有轮次的往来内容与当前提问。随对话推进线性累加，是窗口增长的主要来源之一。
临时层（工具返回、检索片段）接口数据、检索到的文档片段、文件内容。单次体量可能极大，容易在几步之内吃掉大部分预算。

🚀 六、一个具体应用场景

一个接入检索增强（RAG）的客服助手，需要依据产品手册回答用户问题。典型的一轮流程是： 用户提问 → 检索系统取回若干文档片段 → 片段与历史对话一起送入窗口 → 模型给出回答。
问题出在检索片段上：如果为了"保险"一次塞入十几段材料，其中大部分与问题只是语义相近但并不真正作答， 这些片段会挤占预算、并把真正有用的那一段推向窗口中部。检索系统只负责取回，取多少、放几段、怎么排序属于应用侧的预算决策。 工程上常见的做法是：先放宽召回，再用重排序模型（cross-encoder）精排，只把排在最前的高相关片段送入窗口， 并把最关键的内容安排在开头或结尾的位置。

⚠️ 七、易混与边界

  • 把窗口大小等同于模型能力。窗口是"能接收多少"的容量规格，不等于"能可靠使用多少"。研究显示，随着输入变长，模型的准确率会持续下降，这一现象被称为 context rot（上下文腐化）；且这种下降在远未填满窗口时就已开始。
  • 把上下文窗口当作长期记忆。模型本身是无状态的，每次推理都从零开始。窗口只是本次请求的工作区，会话结束即失效。跨会话的"记忆"需要应用层用数据库或向量检索显式地重新送入，而不是模型自带的属性。
  • 以为扩大窗口就能替代检索。相关但错误的干扰文档比明显无关的内容危害更大，因为它们看起来可信。把语料整段塞进窗口，往往同时推高了成本并降低了准确率；检索的价值在于筛选，而不只是搬运。
