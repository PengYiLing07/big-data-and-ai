📖 三、概念的通俗解释

硬盘上的文件本质上只是一串字节，它自己不带「我是用什么编码写的」这张标签。open() 做的是在程序与这个字节序列之间架一条通道，并返回一个文件对象（一种流）；随后所有的读写都发生在这条通道上，而不是直接操作硬盘。文本模式下，读文件是把字节解码成字符串（str），写文件是把字符串编码成字节写出去；二进制模式下不做这两步转换，读写的是 bytes 对象。

因为编码与解码必须是同一张对照表，所以「编码」这件事本质上是一次双向映射：同一个汉字，在 UTF-8 表里对应三个字节，在 GBK 表里对应两个字节。写的时候用了哪张表，读的时候就必须用哪张表。用 A 表写、用 B 表读，得到的就是乱码——这不是文件坏了，而是翻译用错了词典。

中文乱码的根因，就是编码与解码用了两张不同的字节映射表。UTF-8 与 GBK 是两套独立设计的映射规则，字节的切分方式都不同：UTF-8 的中文字符一般占 3 个字节，GBK 的中文字符固定占 2 个字节。把 GBK 的字节按 UTF-8 的规则去切，往往在第一刀就切不下去——Python 会直接抛出 UnicodeDecodeError，提示某个字节不是合法的起始字节。

为什么 Windows 上旧版 Excel 导出的 CSV 常常是 GBK？一是 CSV 格式本身「没有唯一标准」，不同应用程序读写的数据会存在细微差别，编码信息也不写在文件里；二是打开 CSV 的程序会按本机地区设置去猜编码，中国内地简体中文环境下的默认代码页是 GBK（代码页 936），所以旧版 Excel 用「CSV（逗号分隔）」另存出来的文件通常是 GBK 字节。Python 若不显式指定 encoding，用的是与平台相关的默认编码，Windows 上通常也不是 UTF-8，两边一错位就会出现乱码或报错。

💡 一个类比 文件可类比为一只贴着封条的快递箱：箱子里装的是字节，封条上没有写明「本箱按哪套编码打包」。读取文件相当于按某本词典逐字翻译箱内内容——拿对词典就还原出原文，拿错词典就得到一串看似汉字、实际毫无意义的字符。这一类比属于帮助理解的通俗化说法，非官方原文。
💡 一个类比 编码与解码可类比为寄件与收件使用同一套物品编号：寄出时按 A 编号表把「一叠稿纸」编号投箱，收件时若按 B 编号表去查，就会把这叠稿纸读成完全不同的东西。要避免出错，最稳妥的做法是在每次寄件与收件时都明写用哪套编号表——这正是 encoding="utf-8" 的作用。这一类比属于帮助理解的通俗化说法，非官方原文。

⚙️ 五、核心机制 / 组成

一次完整的文件操作由「打开 → 选择模式 → 指定编码 → 读写 → 关闭」五步构成。前两步决定通道能不能建立，第三步决定字节与字符之间的翻译方式，第四步决定数据怎么流动，第五步决定数据是否真的落到磁盘上。

open() 的关键参数

参数作用 / 说明
file文件名的字符串。可以是相对路径（相对于程序运行时的当前工作目录），也可以是绝对路径。
mode描述文件使用方式的字符串，可选，省略时的默认值为 'r'。
encoding文本模式下使用的编码名。省略时用的是与平台相关的默认编码；因为 UTF-8 是现代事实上的标准，官方建议除非确知需要使用别的编码，否则显式写出 encoding="utf-8"。
newline控制换行符的处理方式。用 csv 模块读写文件时，打开文件应设置 newline=''，否则可能出现多余空行。
with 语句处理文件对象时的推荐写法：子句体结束后文件会正确关闭，即便触发异常也可以，且比等效的 try-finally 简短得多。不用 with 就应调用 f.close()。

mode 取值对照

写法含义需要注意
'r'只读，默认值文件不存在时报错
'w'只写；现有同名文件会被覆盖覆盖是不可逆的，写之前要确认目标文件名
'a'追加；写入的数据自动添加到文件末尾适合逐条累积日志、台账
'r+'打开文件进行读写较少使用
加 'b'，如 'rb'二进制模式，读写 bytes 对象二进制模式下不能指定 encoding；处理 JPEG、EXE 等文件时必须用二进制模式，否则换行符转换会破坏数据

四种读法与适用场合

读法行为适用场合
f.read()省略 size 时读取并返回整个文件内容；到达末尾后返回空字符串文件不大、需要整体当一段文本处理
f.readline()读取单行，字符串末尾保留换行符；返回空字符串即表示已到文件末尾按需读取少量行
f.readlines() / list(f)把所有行读成一个列表行数可控，且需要对行做多次遍历
for line in f:循环遍历文件对象，逐行取出大文件的首选；高效利用内存，快速，代码简单

csv 模块的两类对象

对象读写的内容关键用法
csv.reader / csv.writer序列（列表）每一行返回一个字符串列表；writerow() 写一行，writerows() 写多行
csv.DictReader字典第一行默认用作字段名并从结果中去除；可显式传入 fieldnames
csv.DictWriter字典fieldnames 是必填参数，决定写入顺序；writeheader() 写出表头行
常用格式参数—delimiter（分隔符，默认逗号）、quotechar（引号字符，默认双引号）、dialect（如 'excel'、'unix'）

以上内容引自 Python 官方教程第 7 章 7.2 节、《io》模块文档与《csv》模块文档。补充一点：《csv》文档说明 CSV 格式在 RFC 4180 推出很多年前就已被使用，当时并没有合理的标准，不同应用程序读写的数据会存在细微差别，因此处理多个来源的 CSV 文件会比较困难。

🚀 六、一个具体应用场景

一批采访记录从旧版 Excel 导出成 CSV，文件里带着多余空格、空行和空记录。目标是读进程序、清洗并统计，最后把干净的结果写成一份新的 CSV——新文件统一用 UTF-8，方便交给后续的 pandas 环节继续处理。这段代码可以直接运行，用到的全部是标准库。 

# csv_pipeline.py —— 读采访记录 CSV → 清洗统计 → 写回新文件
import csv

SRC = "interview_notes.csv"   # 来自旧版 Excel，实际编码是 GBK
DST = "cleaned_summary.csv"   # 输出统一用 UTF-8

# ① 先造一份 GBK 编码的样例数据（真实流程里这一步由 Excel 完成）
rows = [
    ["编号", "受访者", "记录", "字数"],
    ["001", "张记者", "  地铁票价调整 后，首周客流下降 3%。  ", "18"],
    ["002", "李编辑", "社区加装电梯 的推进难点在哪？", "15"],
    ["003", "王摄影", "   ", "0"],
]
with open(SRC, "w", newline="", encoding="gbk") as f:
    csv.writer(f).writerows(rows)

# ② 读入：encoding 必须与文件实际编码一致；newline="" 交给 csv 模块处理换行
good, skipped = [], []
with open(SRC, newline="", encoding="gbk") as f:
    for row in csv.DictReader(f):           # 第一行被用作字段名
        text = " ".join(row["记录"].split())   # 清洗：压缩连续空白
        if not text:                        # 空记录：跳过并记账
            skipped.append(row["编号"])
            continue
        good.append({"编号": row["编号"],
                     "受访者": row["受访者"],
                     "记录": text,
                     "字数": len(text)})

# ③ 写回新文件：显式声明 UTF-8，并用 DictWriter 写出表头
with open(DST, "w", newline="", encoding="utf-8") as f:
    writer = csv.DictWriter(f, fieldnames=["编号", "受访者", "记录", "字数"])
    writer.writeheader()
    writer.writerows(good)

print("写入", len(good), "行；跳过空记录", skipped)
print("总字数", sum(r["字数"] for r in good))

这一段是文章级别的示例，用于说明「读入—清洗—写回」的完整流转，属于辅助理解示例，非某个来源的原文代码。有一点值得留意：第 ② 步如果把 encoding 写成 "utf-8"，读 GBK 文件会直接抛 UnicodeDecodeError；反过来写文件的编码若与后续工具期望的不一致，下一环就会读到乱码——所以编码要在读写两端都写明。

⚠️ 七、易混与边界

  • encoding 不是可有可无的装饰，而是必须写明的约定。不指定时用的是与平台相关的默认编码（取决于语言区域设置），很多 Windows 用户的区域编码并不是 UTF-8。官方文档明确说明：这正是「在 Unix 上正常、在 Windows 上报错」这类问题的来源，因此强烈建议打开文本文件时显式指定编码。
  • 「写 utf-8」不等于「一定不出乱码」。编码要按文件的实际编码来填。读一个 GBK 生成的 CSV 时，正确做法是写 encoding="gbk"；写 utf-8 可能当场抛出 UnicodeDecodeError，也可能恰好不报错但读出一串无意义字符。常见误解是把乱码一律当成「文件坏了」，实际上文件通常完好，只是翻译用错了表。
  • 文本模式与二进制模式不能混用。文本模式读写的是字符串，并按指定编码完成编解码；二进制模式读写的是 bytes，不做编解码、也不做换行转换，因此在二进制模式下不能指定 encoding。文本模式下默认会把平台特定的行结束符转成 \n，写回时再转回去——这对方便处理文本文件，但会破坏 JPEG、EXE 等二进制文件的数据。
  • 用 csv 模块时必须写 newline=''。官方文档对 csv.reader 与 csv.writer 都说明：如果传入的是文件对象，打开它时应设置 newline=''。原因是 csv 模块自己负责生成行结束符，若再让文本模式做一次换行转换，Windows 上就容易多出空行。
  • 大文件不要用 read() 一把读进来。read() 省略 size 时会读取并返回整个文件的内容，官方提示「文件大小是内存的两倍时会出现问题」；readlines() 同样会把所有行装进列表。逐行迭代整个文件对象则能高效利用内存、快速且代码简单。
  • 相对路径相对于「当前工作目录」，不是脚本所在目录。同一段带上相对路径的代码，从不同目录启动时读到的可能是完全不同的文件。要避免这一不确定性，可以用绝对路径，或先确认当前工作目录。
  • 用 'w' 打开会覆盖同名文件。这不是编码问题而是模式问题：'w' 表示只写，现有同名文件会被覆盖；需要保留原有内容、只在末尾补充时应用 'a'。写文件时若没有用 with、也没有调用 f.close()，即使程序正常退出，写入的参数也可能没有完全落到磁盘上。
